# Theming

UI color/font themes. Each theme is a **YAML file in a directory**, loaded by the
Go backend at request time and applied client-side by overriding CSS custom
properties on `<html>`. No build step, no restart — drop a YAML in the themes
dir and it shows up on the next `GET /api/themes`.

## How it works

1. **Source of truth:** one YAML file per theme in the themes directory (default
   `./themes`). Filename → theme `id` (slugified, extension stripped).
2. **Backend:** `theme.Loader` (`theme/theme.go`) re-reads the directory on every
   `Load()` call (every `GET /api/themes` hit). Missing/empty dir → empty list.
   Malformed files are logged + skipped; other themes still load.
3. **API:** `GET /api/themes` → `{ "themes": [Theme, ...] }`, sorted by name
   (case-insensitive), `Cache-Control: no-store`.
4. **Frontend apply:** `web/src/theme.ts` fetches the list, `applyTheme()` sets
   `--<key>` custom properties on `document.documentElement`, plus fonts, nick
   OKLCH params, `color-scheme`, and `data-theme=<id>`.
5. **Fallback:** if the themes dir is empty/absent, the API returns `[]` and the
   UI keeps the CSS `:root` defaults baked into `web/src/style.css` (Tokyo Night).

### No themes dir required

Themes are an **optional operator overlay**. The shipped default look lives
entirely in `web/src/style.css` `:root`. Theme YAML only *overrides* those vars.

## Theme model (`theme/theme.go`)

YAML fields (all optional except needing at least `colors` to be useful):

| Field | YAML key | Notes |
|-------|----------|-------|
| Name | `name` | Display label in the picker. Defaults to the id. |
| Colors | `colors` | Map of **CSS var name → value**, *without* the `--` prefix. |
| Fonts | `fonts.sans`, `fonts.mono` | font-family stacks |
| Nicks | `nicks.oklch_l`, `nicks.oklch_c` (also `saturation`/`lightness`/`hue_offset`) | hash-derived nick color params |
| Color scheme | `color_scheme` | `dark` or `light`; sets CSS `color-scheme` (default `dark`) |

`id` is not in the file — it's derived from the filename via `slug()`
(lowercase; spaces/`_`/`-` → `-`; other chars dropped).

## Frontend apply (`web/src/theme.ts`)

- `applyTheme(t)`:
  - clears every var in the `THEME_VARS` list from `:root` (so switching themes
    drops stale overrides),
  - sets `--<key>` for each entry in `t.colors`,
  - sets `--sans`/`--mono` from `fonts`,
  - sets `--nick-l` (`%`) and `--nick-c` from `nicks.oklch_l`/`oklch_c`,
  - sets `color-scheme` and `data-theme=<id>`.
- Selection persists in `localStorage["lurker.theme.id"]`.
- `loadInitialTheme()` picks: stored id → else `tokyo-night` → else first theme.
- `theme-ui.ts` `initThemeSelector()` fills the `#theme-select` dropdown and wires
  the change handler (apply + persist). Hides the select if no themes.

### The `THEME_VARS` list matters

`applyTheme` only *clears* vars named in `THEME_VARS` (`web/src/theme.ts`). The
current set:

```
bg-0 bg-1 bg-2 bg-3 bg-4 bg-5 bg-input
fg-0 fg-1 fg-2 fg-3
hair hair-strong
accent accent-soft accent-strong
green yellow orange red magenta cyan
mention mention-soft mention-soft-hover
surface-contrast-fg topicbar-rule
sans mono nick-l nick-c
```

These mirror the `:root` defaults in `web/src/style.css`. A theme can override
any of them. If you introduce a **brand-new** CSS var that themes should control,
add it to both `:root` (default) **and** `THEME_VARS` (so it clears on switch).

## Configuration

Themes dir resolution (`main.go`, `config.go`), highest priority first:

1. `--themes-dir <path>` flag
2. `THEMES_DIR` env var
3. `themes_dir` in config → default `./themes`

## Add a new theme

1. **Create** `themes/<name>.yaml` (filename becomes the id, e.g.
   `solarized-dark.yaml` → id `solarized-dark`):
   ```yaml
   name: Solarized Dark
   color_scheme: dark
   colors:
     bg-0: "#002b36"
     bg-1: "#073642"
     fg-0: "#839496"
     accent: "#268bd2"
     # …override any vars from THEME_VARS you want
   fonts:
     mono: '"JetBrains Mono", ui-monospace, monospace'
   nicks:
     oklch_l: 72
     oklch_c: 0.12
   ```
   Only list the vars you want to override; unset ones fall back to `:root`.
2. **No build/restart needed.** Reload the UI — the theme appears in the picker
   (backend re-reads the dir per request).
3. **Verify:** `curl localhost:8080/api/themes` shows it; pick it in the UI and
   confirm `data-theme="solarized-dark"` on `<html>` and the overridden vars on
   `:root`.

> Note: theme files are operator data, not source. They live in the configured
> themes dir (default `./themes`, which is gitignored-style runtime data), not in
> the web bundle. To ship default themes with a deployment, mount/copy YAMLs into
> that directory.

## Nick colors are separate

Hash-derived nick colors come from `web/src/nick-palette.ts`, generated by
`task gen-palette` (`scripts/gen-nick-palette.mjs`) as perceptually-spaced OKLCH
hues. Themes only tune their **lightness/chroma** via `nicks.oklch_l`/`oklch_c`
(→ `--nick-l`/`--nick-c`); they don't define the hue palette itself.

## Files

| File | Role |
|------|------|
| `theme/theme.go` | YAML loader, `Theme`/`Loader` types, slug logic |
| `api/server.go` | `GET /api/themes` handler (`listThemes`) |
| `main.go` / `config.go` | themes-dir resolution (`--themes-dir`, `THEMES_DIR`, `themes_dir`) |
| `web/src/theme.ts` | fetch, `applyTheme`, `THEME_VARS`, persistence, fallback |
| `web/src/theme-ui.ts` | theme picker dropdown wiring |
| `web/src/style.css` | `:root` default tokens (fallback look) |
| `themes/*.yaml` | the themes themselves (operator-provided runtime data) |
